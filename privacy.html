What it doesn't.

Privacy claims are cheap. This page is the detailed breakdown — what data we store, how encryption actually works, where the gaps are in alpha, and what we're doing about them.

Data model

What the server stores.

Every piece of data that touches our servers, and what form it's in when it gets there.

⚠ Stored in plain text
Your username
Stored as-is. Used for login and display. Choose it accordingly.
Message timestamps
When messages were sent. Not encrypted — metadata is visible to the server.
Server and channel membership
Which communities and channels your account belongs to.

Phone number
Same as email. There is no such field anywhere in the system.
Voice and video streams
WebRTC goes peer-to-peer. Our servers are never in the media path.

Under the hood

How encryption works.

Plain language. No marketing. Here is exactly what happens to your message between your keyboard and the database.

1
You type a message
Your plaintext lives only in your browser or app. It has not been transmitted anywhere yet.
2
Key derivation from your passphrase
When you joined the server, you entered a passphrase. That passphrase was fed through PBKDF2 with a per-server salt to produce a 256-bit AES key. The key is held in memory in your client — it never leaves your device and is never sent to the server.
PBKDF2-HMAC-SHA256 · 200,000 iterations
3
Message encrypted in the browser
Before the message leaves your device, it is encrypted using AES-GCM with a randomly generated 96-bit IV. The result is ciphertext that is mathematically unreadable without the key. Even if the server were completely compromised, the attacker would see random bytes.
AES-GCM-256 · random 96-bit IV per message
4
Ciphertext sent to the server
The encrypted blob, along with the IV and a channel identifier, travels to the server over TLS. The server stores this in PostgreSQL. It has no way to decrypt it — the key was never sent.
TLS in transit · ciphertext-only at rest
5
Recipients decrypt locally
When another member of the server loads the message, their client fetches the ciphertext and IV. Using the same key (derived from the same passphrase), AES-GCM decrypts the message entirely in their browser. The decrypted text is never sent back to the server.
6
Direct messages use per-recipient key exchange
DMs use a separate key exchange so only the two participants can decrypt. The server routes the encrypted payload but cannot read it — it is a blind relay.
E2E · server-blind relay

Honest accounting

Metadata.

Encryption protects content. Metadata is a different problem. Here is what exists and what it reveals.

Metadata item Status What it reveals
Message timestamp Stored plain When you were active, conversation rhythm, response patterns
Sender identity (username) Stored plain That you sent a message to a given channel at a given time
Channel membership Stored plain Which communities and channels you belong to
Online presence Stored plain Whether you're currently online and last-seen time
IP address Standard HTTP — not persisted by default Approximate location if logged; not logged in default deployment
Message content AES-GCM ciphertext only Nothing readable — unrecoverable without the passphrase key
DM content E2E encrypted — never stored Nothing — server never sees plaintext or retains the payload
Voice and video WebRTC P2P — server not in path Nothing — media never touches Recline infrastructure

Metadata minimization is on the roadmap. Future versions will reduce timestamp precision, add optional presence masking, and improve channel membership privacy. This is an active area of work.

Full control

If you self-host,
you own everything.

Running your own Recline instance eliminates all trust assumptions about our infrastructure. You become the server operator.

Your server.
Your data.
Your rules.

When you self-host, messages still arrive as ciphertext (your users' keys never leave their devices), but you control the database, the backups, the log retention policy, and the network configuration. You can verify every line of code in the AGPL-3.0 repository before deploying.

  • No metadata goes to Recline infrastructure — we never see your server's traffic
  • You set your own IP logging policy — default deployment does not log IPs
  • You control database retention — delete message records on any schedule you choose
  • AGPL-3.0 guarantees you can audit and modify every line of server code
  • Three Docker commands to deploy — see the self-hosting guide for details
  • If Recline the company disappears, your self-hosted instance keeps running forever

Honest limitations

What's still
alpha-grade.

We'd rather tell you exactly where the weak spots are than let you assume everything is perfect. Here is the current state.

  • !
    Key management is manual
    Your encryption key is derived from the server passphrase. If you lose it, there is currently no recovery mechanism. A formal key backup and recovery system is on the roadmap. For now: do not lose your passphrase.
  • !
    Metadata is not minimized
    Timestamps, sender identity, and channel membership are stored in plain text. Future versions will reduce timestamp precision and add optional presence masking. This is not solved yet.
  • !
    No independent security audit
    The encryption implementation has not been reviewed by an independent cryptography firm. The code is public and auditable by anyone, but no formal audit has been commissioned yet. We plan to do this before a stable release.
  • !
    Key rotation is not yet implemented
    If a server's passphrase is compromised, there is no current mechanism to rotate keys and re-encrypt history. Adding key rotation is planned for a future release.
  • !
    WebRTC uses STUN for peer discovery
    Voice and video calls use WebRTC P2P, which requires STUN to negotiate the connection. STUN exposes your IP address to call participants. No TURN relay is used — traffic is P2P after negotiation, but STUN server operators can observe that a connection was requested.
  • !
    No forward secrecy on channel messages
    Channel encryption currently uses a static key derived from the server passphrase. This means all past messages could be decrypted if the passphrase is ever exposed. Forward secrecy (per-session ratcheting) is a planned future improvement.
  • !
    File uploads are not yet encrypted
    File and image sharing is not yet implemented. When it is added, it will use the same AES-GCM encryption scheme as messages. No unencrypted file storage will be introduced.
